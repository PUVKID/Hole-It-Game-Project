## LEVEL 1 · 프로젝트 소개와 읽는 방법

구멍을 움직여 주변 물체를 흡수하고 더 크게 만드는 게임의 개발 기록입니다. 플레이어가 보는 화면뿐 아니라 물체가 떨어지는 규칙, 미션·남은 시간·보상과 저장이 어떻게 연결되는지 공개 코드로 읽을 수 있습니다. **바로 설치하는 완제품과 개발 소스 보관본은 구분해야 합니다.**

## LEVEL 1 · 실제 기능과 동작 범위

기본 행동은 이동 → 물체 흡수 → 미션과 성장 확인입니다. 시간 안에 목표를 채우는 일반 흐름 외에 프로필·하트·코인·부스터·출석 화면도 후속 구현에 포함됩니다. 예를 들어 출석 화면을 보는 행동과 보상을 실제 받는 행동은 다릅니다. 조회는 코인을 지급하지 않고 수령 함수가 로컬 날짜와 보유량을 바꿉니다.

초기 제품 코드와 Reference라는 후속 구현 계열이 함께 보관되어 있습니다. 최신 Reference 보관본은 8차이며 9차는 제품 스크립트 일부입니다. 번호가 더 크다는 이유만으로 모든 파일을 덮어 조합하면 같은 게임이 되지 않습니다.

## LEVEL 1 · 입력에서 처리와 출력까지

입력은 터치·조이스틱 조작과 미리 준비한 레벨·물체입니다. 게임은 이동과 충돌을 계산하고, 물체 수집을 점수·미션·성장에 반영합니다. 출력은 화면과 남은 시간·승패, 기기에 저장한 진행 상태입니다. **로컬 저장은 이 기기에 남는 기록**이며 인터넷 계정의 결제나 서버 재화 기록이 아닙니다.

## LEVEL 1 · 사용·실험 순서와 확인 방법

먼저 전체 차수표에서 보고 싶은 구현을 고르고 원래 사용 안내를 읽습니다. 실제로 실행하려면 같은 차수의 Unity 장면·모델·그림·프로젝트 설정을 함께 준비해야 합니다. Unity 편집기에서 파일 읽기와 컴파일 오류를 확인한 뒤 플레이를 검증하고, Android 빌드에는 해당 Editor의 Android 모듈·SDK·NDK·JDK를 준비합니다. C# 파일 몇 개를 복사하는 것만으로 APK가 만들어지지 않습니다.

## LEVEL 1 · 결과와 한계를 해석하는 기준

8차는 물체 진입·이탈 이벤트와 지연 성장·원형 게이지를 다룹니다. 프레임당 25개를 활성화한다는 설정은 그 순간 켜는 작업을 나누는 규칙이지 총 물체가 25개라는 뜻이 아닙니다. 화면의 465레벨·1,010물체 문구도 공개 사본에 그 수의 자산이 모두 있다는 증거가 아닙니다. **소스 설명·편집기 플레이·실제 휴대전화 성능을 각각 확인합니다.**

## LEVEL 1 · 구현과 핵심 파일을 연결해 읽기

게임 중심 흐름은 GameManager 또는 ReferenceGame에서 시작하고 물리·레벨·화면 표현은 관련 파일로 나뉩니다. ReferenceProfile은 보유 재화와 저장, ReferenceAttendance는 날짜별 출석 처리를 맡습니다. 코드를 처음 읽는다면 아래 전체 근거의 입력·출력 표 → 차수 변화 표 → 빠른 시작 → 문제 해결 순서로 읽고, 모르는 파일 이름은 연결된 해당 역할의 코드에서 확인합니다.

## LEVEL 1 · 용어와 실수하기 쉬운 구분

Unity는 화면·장면·입력·물리를 함께 구성하는 게임 제작 환경입니다. 씬은 물체와 화면을 배치한 장면이고, 에셋은 모델·그림·소리 같은 자원입니다. 강체는 중력과 충돌 계산을 받는 물체, 충돌체는 부딪히는 범위를 뜻합니다. 트리거는 범위 진입·이탈을 알려 주는 감지 장치입니다. 객체 풀은 만들어 둔 물체를 다시 쓰는 방식이고, 프레임은 화면·게임을 갱신하는 한 번의 단위입니다.

**공개 코드 보관본과 완전한 Unity 실행 프로젝트는 다릅니다.** 초기 HoleItBuilder와 후속 ReferenceBuilder 계열을 섞지 않습니다. 로컬 코인·하트·출석은 서버 결제·계정 동기화가 아니며, 과거 캐시 삭제·Gradle 복구 도구는 일반 플레이 절차로 실행하지 않습니다.

## LEVEL 1 · 항목별 자세한 풀이와 확인 지점

### LEVEL 1 · 두 구현 계열과 게임 상태

초기 게임과 후속 Reference는 같은 파일을 조금씩 바꾼 한 묶음으로 섞어 쓰면 안 됩니다. 시작 준비·실제 플레이·종료는 서로 다른 단계이며, 잠시 멈추면 입력과 시간 진행도 함께 멈춥니다. 이전 플레이의 물체를 재사용하더라도 보상이 또 지급되지 않도록 시도를 구분합니다.

### LEVEL 1 · 최신차수에서 달라진 점

8차에서는 물체가 감지 범위에 들어오고 나가는 소식을 실제 수집에 연결합니다. 먹은 순간의 성장 목표와 조금 뒤 실제 크기 변화가 구분됩니다. 9차 파일이 있다고 완전한 최신 게임 설치본이 추가된 것은 아닙니다.

손가락 조작과 배치된 물체가 입력이고 이동·흡수·성장 계산이 처리입니다. 결과는 화면과 게임 진행 기록입니다. 화면만 움직인다고 저장이나 미션까지 정상이라고 판단하지 않습니다.

[이 항목의 전체 조건·원문](#source-section-5)

### LEVEL 1 · 주요 기술과 차수 구분

Unity 버전과 Android 빌드 모듈은 게임을 열고 휴대전화용 파일을 만드는 환경입니다. 예전 제작 도구와 나중 제작 도구가 만드는 게임이 달라 같은 것으로 섞지 않습니다.

### LEVEL 1 · 성장·카메라·물리 구성

먹은 점수는 성장 목표에 쌓이고 조금 뒤 크기에 적용됩니다. 카메라가 함께 바뀌어 커진 구멍을 보여 줍니다. 설정표의 속도·중력·간격은 게임 규칙이며 실제 휴대전화의 빠르기를 측정한 값이 아닙니다.

### LEVEL 1 · 빠른 시작

소스만 받는 것과 게임을 실행할 준비가 되는 것은 다릅니다. 같은 차수의 장면·모델·그림·설정을 준비해 Unity에서 오류를 확인한 뒤 플레이하고 빌드합니다.

[이 항목의 전체 조건·원문](#source-section-11)

### LEVEL 1 · 게임 데이터와 설정

8차의 출석은 **31회 누적 주기**이며 보상은 게임 코인 1,000개입니다. 출석 화면을 조회하는 것과 실제 수령은 다릅니다. 수령 함수가 기기의 로컬 날짜와 주기를 확인해 같은 날짜의 중복 수령을 거부하고 재화를 갱신합니다. 서버가 날짜나 보상을 검증하는 구조는 아닙니다.

하트는 최대 5개이고 회복 간격은 1,800초입니다. 승리 보상 상수는 20, 부스터 가격 상수는 1,800, 하트 충전 가격 상수는 900입니다. 이 값들은 게임 코드의 규칙이며 실제 결제 금액이 아닙니다. 무료 플레이·챌린지·일반 캠페인은 비용 처리 방식이 달라 숫자 하나를 모든 모드의 공통 비용으로 읽지 않습니다. 코인·하트·잠금 해제·부스터·출석은 PlayerPrefs라는 기기 로컬 저장소에 남습니다. 계정 동기화나 서버 재화 연동이 완료됐다는 뜻은 아닙니다.

코인·하트·부스터·출석은 게임 안에서 쓰는 값입니다. 출석 화면 보기와 실제 받기는 다르며 같은 날 다시 받지 못할 수 있습니다. 인터넷 결제·계정 서버와 연결한 기록이 아닙니다.

## 두 구현 계열과 게임 상태

초기 제품 계열에서는 `GameManager`가 입력·미션·레벨·홀·UI 참조를 연결합니다. 후속 Reference 계열은 `ReferenceGame`의 부분 클래스로 게임·물리·레벨·화면을 나눕니다. 서로 다른 계열의 스크립트와 씬을 같은 시점 프로젝트처럼 섞지 않습니다. 보존된 8차 Reference 구현과 9차 제품 스크립트 8개는 자료 범위가 다릅니다.

제품 GameManager 코드의 상태 흐름은 다음과 같습니다.

- 시작: 필수 참조와 성장표 검사 후 Loading→Title→Ready→Playing으로 전환합니다.
- 수집과 종료: 소비한 물체의 점수·성장·미션을 반영합니다. 목표 완료는 Clearing→LevelClear, 시간 소진은 Failed로 이어집니다.
- 보상: SessionId와 보상 소유권 검사로 이전 세션의 풀링 객체가 중복 지급하는 경로를 막습니다.
- 일시정지: Pause는 시간 배율 0과 입력 중단, Resume는 배율 1과 Playing 복귀이며 포커스 상실도 일시정지합니다.

Reference 8차에서는 진입·이탈 트리거, 지연 성장, 열린 원형 게이지를 변경했습니다. 프레임당 25개 활성화와 성장 지연 0.3초는 처리 설정이며 실제 FPS나 전체 강체 수 제한을 뜻하지 않습니다.

프로필·재화·하트·출석은 로컬 게임 상태이며 서버 결제나 계정 동기화와 다릅니다.

실행에는 같은 차수의 Unity 씬·Packages·ProjectSettings·모델/텍스처·직렬화 참조가 필요합니다. 공개 C#만 있는 부분본은 코드 흐름과 비교를 읽는 자료입니다. Builder와 복구/캐시 도구는 자산을 바꿀 수 있으므로 일반 플레이 명령처럼 일괄 실행하지 않습니다. 각 차수의 카탈로그·물리·저장 클래스와 실제 전체 차이는 아래 독립 안내에서 이어집니다.

<a name="️-1차부터-8차까지-달라진-점"></a>
<a id="source-section-9"></a>
### 1차부터 8차까지 달라진 점

**차수:** 1차

**구현 변화:** 미션 최대 3개, 객체 풀, 레벨 기록과 타이머를 갖춘 수집 프로토타입. Transform 기반 끌기·낙하와 반지름 보간

**차수:** 2차

**구현 변화:** 쌓인 물체의 중력·깨우기와 월드 좌표 드래그, 폭탄 소비 실패, 폭탄 처리 중 승리 유예

**차수:** 3~4차

**구현 변화:** ReferenceCatalog 기반 모델·배치·목표, 최대 1,023개 단위 묶음 렌더링과 30레벨 상한. 3차 터치 중 조이스틱에서 4차 상시 표시로 변경

**차수:** 5차

**구현 변화:** 별도 LocalPhysics3D 장면과 강체 풀 384개, 비동기 로딩, 로컬 코인·하트·부스터 상점

**차수:** 6차

**구현 변화:** TMP 글꼴, 챌린지·3D 도감·31일 출석, 배치 장애물과 랜덤 폭탄

**차수:** 7차

**구현 변화:** 성장 단계별 속도·카메라 전환, 첫 입력부터 시작하는 타이머, 가까운 목표 최대 5개를 0.1초마다 탐색

**차수:** 8차

**구현 변화:** 모든 배치 물체의 강체·충돌체 유지, 실제 트리거 수집 이벤트, 지연 성장과 열린 원형 게이지, 전체 경계 상자를 이용한 시야 검사


8차의 프레임당 활성화 25개는 전체 강체 수 제한이 아닙니다. 7차까지 남아 있던 강체 풀 384개 제한과 일부 원격 물체의 대체 낙하를 8차의 동작으로 설명하지 않습니다. 초기 직교 카메라와 후기 원근 카메라, 1차 이동 속도 8과 7차 이후 기본 속도 2.6도 서로 다른 구현입니다.

<a name="-성장카메라물리-구성"></a>
<a id="source-section-10"></a>
### 성장·카메라·물리 구성

8차 `ReferenceGrowthProgress`는 수집 점수를 누적하고 0.3초 뒤 다음 성장 단계를 적용합니다. 진행 링은 128분할 메시로 그리며, `ReferencePhysicsTrigger`는 진입·이탈 이벤트를 게임 소유자에게 전달합니다.

| 설정 | 후속 Reference 코드 값 |
| :--- | :--- |
| 물리 성장 단계 상한 | 10 |
| 이동 속도 | 시작 2.6, 단계당 0.442 증가, 부스트 계수 1.3 |
| 카메라 시야각 | 25 → 44, 전환 0.3초 |
| 중력·물리 간격 | 35, 0.02초 |
| 성장 표현 | 0.3초 확대 후 0.15초 복원 |

일부 구현 주석은 참조한 원본 데이터와 RVA를 기록합니다. Android 빌드 스크립트의 500MB 조건은 전체 에셋을 포함한 패키지의 크기 검사입니다.

3. Unity Editor에서 임포트·컴파일 오류를 확인한 뒤 프로젝트의 테스트와 플레이 검증을 수행합니다.
4. Android 빌드에는 해당 Editor의 Android 모듈·SDK·NDK·JDK가 필요합니다.

완전한 8차 프로젝트를 준비한 환경에서 제공된 빌드 진입점은 다음과 같습니다.

```powershell
cd "8차/Source"
.\Build-Android.ps1 -UnityPath "C:\Program Files\Unity\Hub\Editor\6000.3.6f1\Editor\Unity.exe"
```

빌드에는 소스 외에 해당 차수의 씬·에셋·프로젝트 설정이 필요합니다. 스크립트는 전체 에셋을 포함한 원본 패키지의 APK 크기 조건도 검사합니다.

## 게임 데이터와 설정

| 항목 | 8차 코드의 값·처리 |
| :--- | :--- |
| 출석 주기 | 31회 누적 |
| 출석 보상 | 1,000 게임 코인 |
| 중복 수령 | 같은 로컬 날짜 재수령 거부 |
| 하트 상한 | 5 |
| 하트 회복 간격 | 1,800초 |
| 승리 보상 상수 | 20 |
| 부스터 가격 상수 | 1,800 |
| 하트 충전 가격 상수 | 900 |

코인·하트·잠금 해제·부스터·출석 상태는 로컬 PlayerPrefs에 저장합니다. 실제 결제나 서버 재화 연동은 구현 범위에 포함되지 않습니다. 무료 플레이·챌린지·일반 캠페인은 비용 처리 방식이 다릅니다. 미션 목표 수와 수집 성장 포인트도 별도로 관리합니다.

출석 조회는 보상을 소비하지 않고, 수령 함수가 날짜·주기와 재화를 갱신합니다. 이는 기기 로컬 날짜를 사용하는 구현이며 서버 검증형 보상 시스템은 아닙니다. 초기 차수의 성장 표·미션·레벨 수를 후속 차수에 그대로 적용하지 않습니다.

<a name="-실행시험-범위"></a>
<a id="source-section-13"></a>
### 실행·시험 범위

Unity 컴파일과 플레이 검증, Android 빌드와 실제 기기 성능 평가는 각 실행 환경에서 수행합니다.

후기 실행에는 ReferenceCatalog와 모델·충돌 메시·배치/장애물 메타데이터, 스타일·음원·글꼴·TMP 텍스트 프리셋이 필요합니다. 화면의 `465레벨`·`1,010물체` 문구는 공개 사본의 실제 자산 수를 보증하지 않습니다. 일부 코드가 원본 데이터·배치를 참조하므로 모든 모델과 그림을 직접 제작한 것으로 설명하지 않습니다.

Windows 캡처·시험 도구에는 버튼 호출, 폭탄 배치, QA 저장 상태 초기화와 시험용 이동이 포함됩니다. 사용하는 차수의 도구를 확인하고 별도 시험 상태에서 실행해야 합니다. 정지 장면 180프레임 기록과 순간 이동·시간 가속을 사용한 기능 시험을 제공합니다. Android 성능과 일반 조이스틱 플레이는 별도로 평가합니다.

<a name="️-편집기시험복구-도구를-사용할-때"></a>
<a id="source-section-14"></a>
### 편집기·시험·복구 도구를 사용할 때

**도구 묶음:** Editor 제작 도구

**실제 동작과 준비 조건:** 메시·텍스처·프리팹·레벨·씬·프로젝트 설정을 생성하거나 덮어씁니다. 선택한 차수의 에셋과 함께 사용해야 합니다.

**도구 묶음:** 오프라인 정적 검사

**실제 동작과 준비 조건:** 설정·참조·메시·UI 계산 등을 확인하지만 C# 컴파일·PhysX·실제 기기 플레이까지 실행하는 검사는 아닙니다.

**도구 묶음:** 캠페인 시험

**실제 동작과 준비 조건:** 순간 이동·반복 탐색·시간 배속·reflection을 사용하는 경로가 있어 정상 조이스틱 조작 완주와 구분해야 합니다.

**도구 묶음:** 이전 캐시 정리

**실제 동작과 준비 조건:** `cleanup_editor_cache.ps1`은 별도 적용 스위치 없이 조건 확인 뒤 `Library`의 `Bee` 외 직계 항목을 삭제합니다. 일반적인 확인 명령으로 실행하면 안 됩니다.

**도구 묶음:** 후속 캐시 정리

**실제 동작과 준비 조건:** `cleanup_editor_cache-fresh2abi.ps1`은 기본 계획 출력, `-Apply`에서 명시한 캐시만 삭제하며 연결 경로와 후손을 검사합니다. 특정 원래 빌드 증거에 의존합니다.

**도구 묶음:** Gradle 복구·시험 집계

**실제 동작과 준비 조건:** 원래 경로·로그·빌드 증거에 결합된 도구입니다. 집계된 과거 PASS는 현재 소스의 새 전체 시험 성공을 뜻하지 않습니다.


[7차 검증 도구](../../7%EC%B0%A8/Verification)는 원래 사건의 복구용 자료를 포함합니다. `fresh2abi` 도구 역시 임의 환경에 바로 적용하는 범용 복구 프로그램이 아닙니다. 이 저장소를 정리하는 동안 캐시 삭제·Gradle 복구·Unity 시험을 실행하지 않았습니다.

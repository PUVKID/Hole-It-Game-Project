# HOLE IT — ULTIMATE UNITY PROJECT COMPLETION PROMPT
## Unity 6000.3.6f1 / Built-in Render Pipeline / Portrait Mobile
### Full Source Integration · Procedural Assets · 30 Playable Levels · Automated Setup · Regression Testing · Final Unity ZIP

너는 모바일 하이퍼캐주얼 게임을 실제 출시 수준으로 제작해 온 시니어 Unity 게임 개발자, 테크니컬 아티스트, 게임플레이 엔지니어, 그래픽스 엔지니어, UI/UX 디자이너, QA 엔지니어, 빌드 엔지니어다.

이번 작업은 단순한 코드 작성이나 예제 프로젝트 제작이 아니다. 첨부된 `HoleIt_Source` Unity 프로젝트를 직접 조사하고, 기존 구현과 에셋을 보존하면서 전체 게임을 완성하고, 가능한 모든 검증을 수행한 후 **실제로 Unity Hub에서 열 수 있는 완성된 Unity 프로젝트 ZIP 파일을 생성하여 제출하는 작업**이다.

최종 목표는 Hole It!의 핵심 게임플레이와 밝고 귀여운 모바일 퍼즐 게임의 분위기를 참고한 독립적인 3D 홀 게임을 제작하는 것이다. 원작의 실제 코드, 모델, 텍스처, 사운드, 로고, 레벨 파일을 복사하거나 추출하지 말고 모든 신규 에셋과 콘텐츠를 자체 생성한다.

질문으로 작업을 중단하지 않는다. 불명확한 부분은 프로젝트를 먼저 조사하고, 합리적인 기본값을 설정하며, 최종 보고서에 가정과 제한사항을 기록한다.

단, 파일이 실제로 존재하는지 확인하지 않고 있다고 주장하거나, 실행하지 않은 테스트를 성공했다고 보고하거나, 만들어지지 않은 ZIP 파일의 다운로드 링크를 만들어 내서는 안 된다.

# 0. 최종 산출물 계약 — ZIP 파일 제출이 최우선

이번 작업에서 가장 중요한 요구사항이다.

**최종 결과물은 수정된 전체 Unity 프로젝트가 들어 있는 실제 ZIP 파일이어야 한다.** 설명만 작성하거나, C# 스크립트 일부만 출력하거나, 변경 방법을 알려주는 것으로 완료하지 않는다.

## 0.1 제출 파일

최종 ZIP 파일명은 다음과 같이 지정한다.

`HoleIt_Source_Completed.zip`

작업 환경에서 파일 생성이 가능한 경우 `/mnt/data/HoleIt_Source_Completed.zip`에 저장한다.

최종 답변에는 해당 파일이 실제로 생성되었고 경로가 확인된 경우에만 유효한 다운로드 링크를 제공한다.

## 0.2 ZIP 내부 구조

ZIP의 루트에는 하나의 완전한 Unity 프로젝트 폴더가 있어야 한다.

권장 구조:

```text
HoleIt_Source_Completed.zip
└── HoleIt_Source/
    ├── Assets/
    │   ├── Scripts/
    │   ├── Editor/
    │   ├── Shaders/
    │   ├── Art/
    │   ├── Materials/
    │   ├── Prefabs/
    │   ├── Scenes/
    │   ├── Data/
    │   ├── Audio/
    │   ├── UI/
    │   └── Tests/
    ├── Packages/
    │   ├── manifest.json
    │   └── packages-lock.json
    ├── ProjectSettings/
    │   └── ProjectVersion.txt
    ├── README_KR.md
    └── BUILD_REPORT.md
```

위 구조는 기준이다. 기존 프로젝트 구조에서 필요한 폴더가 다르다면 모든 파일을 무조건 이동하지 말고 기존 구조를 유지하면서 통합한다.

다음 항목은 유지한다.

- 기존 C# 코드와 신규 코드
- 모든 필수 ScriptableObject
- 모든 필수 씬과 프리팹
- 절차 생성 모델과 머티리얼
- 모든 필수 셰이더
- 프로젝트 설정
- 패키지 매니페스트와 잠금 파일
- 필요한 메타 파일과 GUID
- 자동 빌드 및 최초 실행 도구
- 테스트 코드와 검증 자료
- 한국어 README와 빌드 보고서

Unity에서 다시 생성되는 `Library`, `Temp`, `Obj`, `Logs`, 불필요한 IDE 캐시 등은 일반적으로 ZIP에서 제외한다. 다만 프로젝트 실행에 꼭 필요한 파일을 단지 용량이 크다는 이유로 삭제하지 않는다.

`Packages/manifest.json`, 패키지 버전, 씬, 프로젝트 설정을 누락해서 새 프로젝트처럼 열리지 않는 불완전한 ZIP을 제출하지 않는다.

## 0.3 ZIP 검증

ZIP을 만든 후 다음을 실제로 수행한다.

1. 파일이 존재하는지 확인한다.
2. ZIP 파일 크기를 확인한다.
3. ZIP 내부의 모든 파일 목록을 확인한다.
4. 압축 무결성 검사를 수행한다.
5. Unity 프로젝트 루트가 올바른지 확인한다.
6. 필수 씬과 스크립트가 들어 있는지 확인한다.
7. `manifest.json`의 JSON 문법을 검증한다.
8. `ProjectVersion.txt`의 버전을 확인한다.
9. 참조되는 주요 에셋과 GUID 메타 파일이 포함되었는지 검사한다.
10. 가능하다면 임시 디렉터리에 압축을 풀어 Unity 프로젝트 루트 구조를 다시 확인한다.

Unity 에디터가 설치된 작업 환경이라면 실제 Unity 배치 모드 컴파일과 빌드까지 시도한다. Unity가 설치되어 있지 않거나 라이선스·플랫폼 모듈 등의 이유로 실행할 수 없다면 정적 검사까지만 진행했다고 정확히 보고한다.

ZIP을 만들기 전에 반드시 전체 소스 파일과 신규 에셋을 완성한다. 최종 결과물을 만든 후 변경사항이 생겼다면 ZIP을 다시 생성하고 재검증한다.

**최종 답변의 주 산출물은 전체 Unity 프로젝트 ZIP이며, 모든 핵심 소스는 ZIP 내부에 포함한다. 채팅에 모든 소스 파일을 중복해서 출력하는 것은 필수가 아니다.**

# 1. 프로젝트 분석과 기존 작업물 보존

작업을 시작할 때 첨부 파일 또는 현재 작업공간에서 실제 `HoleIt_Source` 프로젝트를 찾는다.

가능하면 먼저 기존 프로젝트의 전체 디렉터리 구조와 주요 파일을 읽는다.

첨부된 프로젝트를 실제로 찾을 수 없다면 빈 프로젝트를 기존 프로젝트인 것처럼 꾸미지 않는다. 이 경우 입력 프로젝트가 확인되지 않았다는 사실을 명확히 보고한다.

## 1.1 프로젝트 환경

기본 목표 환경은 다음과 같다.

- Unity 6000.3.6f1
- Built-in Render Pipeline
- 모바일 세로 화면
- Android 우선 빌드
- 모바일 터치 조작
- 에디터에서 마우스 기반 조작 테스트 지원

실제 프로젝트 버전이 명시한 버전과 다르다면 프로젝트 내부의 `ProjectSettings/ProjectVersion.txt`와 실제 에디터 환경을 확인한다.

현재 프로젝트에 이미 설치된 패키지와 플러그인을 조사한다. 필요한 이유가 없다면 패키지를 임의로 교체하거나 전체 버전을 무작정 최신으로 올리지 않는다.

## 1.2 조사 대상

다음 영역을 확인한다.

- `Assets/Scripts`
- `Assets/Editor`
- `Assets/Shaders`
- `Assets/Scenes`
- `Assets/Prefabs`
- `Assets/Materials`
- `Assets/Data` 또는 기존 데이터 폴더
- `ProjectSettings`
- `Packages`
- 기존 메인 씬
- 기존 게임 매니저
- 기존 홀과 흡수 시스템
- 기존 가상 조이스틱
- 기존 레벨 스포너
- 기존 이펙트 풀
- 기존 셰이더
- 기존 ScriptableObject 데이터
- 기존 저장 시스템
- 기존 에디터 자동 생성 도구

유사한 역할을 하는 기존 클래스가 있다면 내용을 읽고 재사용 여부를 결정한다.

`HoleController`, `HoleSwallow`, `HoleConsume`, `LevelManager`, `LevelSpawner`, `ObjectPooler`, `VirtualJoystick`, `GameManager`, `PerformanceGovernor`, `LevelData` 같은 클래스가 이미 있다면 무조건 새로 만들지 않는다.

기존 코드가 올바르게 작동한다면 유지한다. 오류가 있다면 근본 원인을 수정한다. 기존 코드와 신규 코드가 중복되어 같은 이벤트를 두 번 처리하지 않도록 한다.

## 1.3 변경 내역 기록

작업 전에 기존 파일 목록과 핵심 설정을 기록한다. 가능하다면 Git 또는 변경 내역 파일을 사용한다.

작업 중 기존 파일을 삭제하거나 대규모로 재구성하기 전에 해당 파일이 어디에서 사용되는지 확인한다.

사용자가 추가한 변경사항을 강제로 초기화하지 않는다.

새로 생성한 파일, 수정한 파일, 사용하지 않게 된 파일은 최종 보고서에서 구분한다.

# 2. 게임 디자인 목표

게임은 단순히 주변 물체를 모두 삼키는 일반적인 IO 게임이 되어서는 안 된다.

핵심은 다음 세 가지다.

1. 현재 홀 크기로 삼킬 수 있는 물체가 무엇인지 판단한다.
2. 레벨에 설정된 특정 임무를 달성하기 위해 이동 경로와 흡수 대상을 선택한다.
3. 제한 시간, 성장 단계, 방해 요소, 오답 규칙을 고려하여 임무를 완성한다.

원작의 고유 리소스를 사용하지 않으면서도 다음과 같은 장르적 특징을 구현한다.

- 손가락을 이용한 간단한 이동
- 바닥에 배치된 다양한 소품
- 물체가 홀 안으로 끌려 들어가는 애니메이션
- 흡수에 따른 홀 성장
- 미션 아이콘과 진행도
- 짧고 명확한 레벨 단위 진행
- 밝고 채도 높은 3D 아트 스타일
- 짧은 시간에 플레이할 수 있는 모바일 게임 루프
- 클리어 및 실패 피드백
- 다음 레벨과 해금 시스템

게임 제목과 로고는 독자적으로 제작한다. 원작의 로고 이미지, 고유한 아트워크 또는 추출 리소스를 사용하지 않는다.

## 3.2 게임 상태

게임 상태는 중앙 시스템을 통해 관리한다.

필요한 상태 예시:

- Boot
- MainMenu
- Loading
- Countdown
- Playing
- Paused
- LevelClear
- LevelFailed
- Results
- ReturningToMenu

상태 전환은 유효한 경로를 통해서만 발생하도록 한다.

게임이 종료된 후 점수가 계속 증가하거나, 일시정지 중 물체가 계속 삼켜지거나, 이전 레벨의 비동기 작업이 다음 레벨의 상태를 변경하지 않도록 한다.

씬을 다시 불러오거나 레벨을 재시작할 때 기존 코루틴, 이벤트, 참조, 점수, 타이머, 흡수 대기열이 제대로 정리되어야 한다.

# 4. 3D 아레나 구성

## 4.1 모바일 세로 화면

게임은 세로 화면을 기준으로 설계한다.

- 초기 화면 방향은 Portrait
- HUD는 Safe Area 안에 배치
- 상단에는 미션 정보와 타이머
- 중앙에는 플레이 공간
- 하단에는 이동 입력
- 중요한 버튼끼리 겹치지 않도록 한다.
- 화면 비율이 달라도 UI가 잘리지 않아야 한다.

기준 해상도만을 위해 UI를 고정된 픽셀 좌표에 배치하지 않는다.

`Canvas Scaler`, Anchors, Pivot, Safe Area를 활용한다. UI가 화면 크기에 따라 과도하게 확대되거나 축소되지 않도록 최소·최대 크기를 설정한다.

## 4.2 아레나

아레나는 한눈에 플레이 영역을 이해할 수 있도록 구성한다.

- 격자 기반 바닥
- 테마별 색상
- 플레이어가 이동할 수 있는 경계
- 광장처럼 비워 둔 시작 영역
- 서로 다른 크기의 소품
- 배경 장식
- 자연스러운 조명과 그림자
- 홀과 대상 물체가 쉽게 식별되는 색상 대비

홀의 이동 범위는 화면에 보이는 플레이 영역과 일치해야 한다. 바닥 밖으로 나가거나 시각적으로 보이는 경계와 이동 가능 범위가 불일치하는 문제를 방지한다.

## 4.3 체크무늬 바닥

기본 바닥은 보라색 또는 테마에 맞는 캔디톤 체크무늬로 구성한다.

체크무늬가 단순한 평면 스프라이트처럼 보이지 않게 적절한 명암과 재질을 준다.

바닥 무늬의 크기는 카메라 거리와 맵 크기에 따라 자연스럽게 보여야 한다.

멀리 있는 무늬가 지나치게 촘촘해져 깜빡이거나 모바일 화면에서 불필요한 시각적 노이즈를 만들지 않도록 한다.

테마별 바닥은 동일한 기반 머티리얼을 공유하고 색상 또는 파라미터만 변경할 수 있도록 한다.

---

# 5. 홀 모델, 스텐실 마스크, 내부 공간

홀은 게임의 핵심 시각 요소다.

기존에 구현된 홀의 Stencil 마스크, 내부 원통, 가장자리 림 구조를 조사하고 유지·개선한다.

## 5.1 홀의 구조

가능하면 다음 요소를 조합한다.

- 홀 마스크 메시
- 바닥의 마스크 처리
- 내부의 어두운 공간
- 내부 원통 또는 원뿔형 깊이 메시
- 깊이감 있는 내부 그라데이션
- 가장자리 림
- 성장 시 색상과 발광의 변화
- 내부의 미세한 소용돌이
- 흡수 시 반응 애니메이션

홀은 단순한 검은 원판이 되어서는 안 된다. 오브젝트가 입구를 통과한 뒤 실제 구멍 안으로 사라진 것처럼 보여야 한다.

## 5.2 Built-in Render Pipeline 셰이더

현재 프로젝트는 Built-in Render Pipeline을 사용한다. URP 또는 HDRP 전용 셰이더를 기본 해결책으로 사용하지 않는다.

기준 셰이더:

- `HoleMask`
- `HolePit`
- `HoleRim`
- `GroundStencil`

현재 동일한 역할을 하는 셰이더가 있으면 재사용하고 중복 구현하지 않는다.

각 셰이더에서 다음을 검증한다.

- Stencil Ref
- Comp
- Pass
- ReadMask 및 WriteMask
- Render Queue
- ZWrite
- ZTest
- ColorMask
- Cull
- 투명도 처리
- 모바일 플랫폼에서의 동작
- 셰이더 컴파일

Stencil 마스크와 바닥의 렌더 순서는 서로 일치해야 한다.

마스크가 바닥의 잘못된 위치를 제거하거나, 내부 메시가 바닥에 가려지거나, 홀 밖의 물체가 비정상적으로 잘리는 문제가 없어야 한다.

스텐실 버퍼의 상태는 다른 렌더러의 설정에 의해 오염되지 않도록 관리한다.

## 5.3 셰이더 오류 대응

다음 상황을 확인한다.

- 셰이더를 찾을 수 없는 경우
- 셰이더 컴파일 실패
- 마테리얼의 Shader 참조 누락
- 모바일에서 지원하지 않는 연산 사용
- 셰이더의 과도한 연산량
- Built-in 렌더 파이프라인과의 불일치

홀의 시각 효과가 일부 실패하더라도 게임플레이 자체가 중단되지 않게 한다.

대체 머티리얼은 프로젝트 안에 포함하고 실제 존재하는 Shader를 참조한다.

가능하다면 개발용 디버그 옵션을 제공하여 홀 마스크 영역, 판정 반경, 물체 Tier, 실제 흡수 가능 여부를 시각적으로 확인하도록 한다. 디버그 요소는 일반 플레이 화면에서 보이지 않게 한다.

---

# 6. 홀 이동과 입력

## 6.1 기본 조작

기본 조작은 손가락을 화면에 대고 드래그하여 홀을 움직이는 방식이다.

기존의 하단 중앙 고정 조이스틱도 삭제하지 않고 설정에서 선택 가능한 대체 조작 방식으로 유지한다.

기본 모드:

`Drag`

선택 가능한 대체 모드:

`FixedJoystick`

두 모드는 같은 이동 입력 인터페이스를 통해 홀 이동 시스템에 값을 전달해야 한다. 입력 방식마다 별도의 이동 코드를 중복 구현하지 않는다.

## 6.2 드래그 조작

드래그 입력은 다음을 지원한다.

- 손가락을 누르면 이동 시작
- 화면을 드래그하면 입력 방향 갱신
- 손가락을 놓으면 입력 해제
- 다른 손가락의 입력과 혼선 방지
- UI 위에서 누른 입력의 게임플레이 전달 방지
- 게임 일시정지 중 이동 차단
- 결과 화면과 메뉴에서 이동 차단
- 앱이 백그라운드로 전환될 때 입력 초기화
- 화면 회전 또는 해상도 변화 시 입력 상태 복구

터치 위치를 월드 좌표로 직접 변환하여 홀을 순간이동시키지 않는다. 화면 공간 입력을 이동 방향 또는 월드 평면상의 목적지로 변환한 뒤, 적절한 이동 제어를 거친다.

## 6.3 드래그 감도와 이동 보간

이동 시스템은 다음 값을 설정할 수 있게 한다.

- 감도
- 최대 이동 속도
- 가속
- 감속
- 이동 스무딩
- 터치 이동과 월드 이동 사이의 변환 계수
- 최대 이동 범위
- 입력 데드존

홀의 움직임이 갑작스럽거나 무겁지 않도록 한다.

입력 해제 후 홀은 설정된 방식으로 부드럽게 감속한다.

목적지와 홀 사이의 거리가 짧을 때 과도하게 진동하거나 목표 지점을 반복해서 넘나들지 않도록 한다.

프레임률이 달라도 움직임이 지나치게 달라지지 않게 한다.

## 6.4 화면과 월드 좌표

카메라가 쿼터뷰 또는 높은 시점일 때 드래그 방향과 실제 홀의 이동 방향이 최대한 자연스럽게 일치하도록 한다.

화면의 가로 입력이 월드의 X축, 세로 입력이 월드의 Z축으로 어떻게 변환되는지 명확하게 정의한다.

카메라 회전과 플레이어 이동 방향을 중복 적용하지 않는다.

홀의 목표 지점은 아레나의 플레이 범위 안으로 제한한다.

## 6.5 입력 시스템 호환성

Unity 6의 Input System 설정을 실제 프로젝트와 일치시킨다.

프로젝트가 New Input System을 사용하는 경우 다음을 확인한다.

- 입력 패키지 설치 및 버전
- Input Actions
- EventSystem
- UI Input Module
- 터치 포인터
- 마우스 에디터 테스트
- 멀티터치
- 앱 포커스 변경
- 일시정지 후 입력 복구

기본 입력 설정을 무조건 변경하지 않는다. 현재 설정과 코드의 호환성을 확인한 후 가장 안정적인 경로를 선택한다.

Unity 6에서 기본 입력 경로가 New Input System 전용인데 기존 `Input.*` API를 호출하여 예외가 발생하는 문제를 반복하지 않는다.

가능하다면 입력 처리를 한곳으로 집중시키고, 구식 입력 API와 새 입력 API가 동시에 같은 동작을 발생시키지 않도록 한다.

---

# 7. 홀의 Tier, 성장, 흡수 가능 범위

홀과 오브젝트는 공통된 Tier 규칙을 사용한다.

## 7.1 기본 규칙

각 오브젝트에는 게임플레이용 Tier가 있다.

홀은 현재 Tier보다 높지 않은 Tier의 오브젝트만 흡수할 수 있다.

예를 들어 홀의 Tier가 2라면 Tier 1과 Tier 2를 흡수하고 Tier 3은 흡수하지 못한다.

시각적 크기와 논리적 Tier가 서로 다르지 않도록 한다.

오브젝트의 프리팹 Scale, Collider의 Bounds, 부모 Scale이 서로 달라도 논리적 Tier를 일관되게 유지한다.

## 7.2 성장 규칙

흡수한 오브젝트마다 성장 경험치가 축적된다.

성장 시스템에는 다음 값이 필요하다.

- 초기 홀 Tier
- 최대 홀 Tier
- Tier별 시각적 반지름
- Tier별 흡수 판정 반지름
- 오브젝트별 성장 경험치
- 다음 단계에 필요한 경험치
- 최대 성장 경험치
- 성장 계수
- 성장 애니메이션 길이

성장 계산은 중앙에서 관리한다.

기본 공식은 구현과 밸런스 조정이 쉬운 정수 경험치 방식 또는 단조 증가 방식으로 설계한다. 숫자가 무한정 커지거나 NaN/Infinity가 발생하지 않도록 제한한다.

성장 경험치는 해당 물체가 완전히 흡수되는 시점에 한 번만 반영한다.

## 7.3 성장 연출

Tier가 증가할 때 다음을 수행한다.

1. 홀의 실제 크기를 갱신한다.
2. 흡수 판정 반경을 갱신한다.
3. 가장자리 림의 표현을 갱신한다.
4. 성장 링 또는 파티클을 실행한다.
5. 홀의 스케일 펀치 애니메이션을 실행한다.
6. 카메라가 서서히 줌아웃한다.
7. 성장 게이지와 Tier UI를 갱신한다.
8. 성장 효과음을 실행한다.

홀의 렌더링 크기와 흡수 반경이 서로 다른 프레임 상태로 오래 남지 않도록 한다.

---

# 8. 흡수 애니메이션과 처리 순서

오브젝트가 홀에 닿는 즉시 삭제되는 것은 금지한다.

모든 오브젝트는 명확한 흡수 상태를 가진다.

권장 상태:

- Idle
- Eligible
- Attracted
- Tilting
- Falling
- Consumed
- ReturnedToPool

실제 구현은 더 간결해도 되지만 상태 전환이 중복되거나 역행하지 않아야 한다.

## 8.1 흡수 과정

흡수 가능한 물체가 홀의 유효 범위에 들어오면 다음 과정을 수행한다.

1. 현재 홀 Tier와 오브젝트 Tier를 확인한다.
2. 해당 오브젝트의 흡수 가능 여부를 결정한다.
3. 이미 흡수 중인지 검사한다.
4. 이미 점수가 지급되었는지 검사한다.
5. 흡수 대기열에 등록한다.
6. 오브젝트가 홀 중심을 향하도록 이동시킨다.
7. 홀의 가장자리로 끌려가는 모습을 표현한다.
8. 홀의 중심을 향해 기울어지거나 회전하게 한다.
9. 홀 안으로 낙하하는 애니메이션을 적용한다.
10. 낙하하면서 스케일을 감소시킨다.
11. 시각적으로 홀 내부에 들어갔을 때 소멸한다.
12. 점수와 성장 경험치를 반영한다.
13. 미션 진행도를 갱신한다.
14. 필요한 파티클과 사운드를 실행한다.
15. 객체를 풀에 반환한다.

홀의 중심으로 텔레포트시키거나 Collider를 끄고 즉시 삭제하는 단순 구현으로 대체하지 않는다.

## 8.2 다중 흡수

여러 물체가 동시에 홀 안으로 들어와도 순서가 꼬이지 않아야 한다.

흡수 대기열을 사용하거나 충돌 없이 작동하는 동등한 방식을 사용한다.

각 오브젝트의 흡수는 최대 한 번만 등록된다.

다음 문제를 방지한다.

- 한 오브젝트가 여러 번 등록됨
- 점수가 중복 증가함
- 성장 경험치가 중복 적립됨
- 물리 시뮬레이션이 흡수 애니메이션과 충돌함
- 오브젝트가 풀에 두 번 반환됨
- 씬을 바꾼 뒤 이전 흡수 작업이 실행됨

순차 처리의 속도는 설정에서 조정할 수 있게 한다.

## 8.3 흡수 취소 및 예외

다음 상황을 처리한다.

- 레벨 종료
- 일시정지
- 재시작
- 씬 전환
- 오브젝트가 이미 파괴된 경우
- 풀에서 반환된 경우
- 대상 Collider가 비활성화된 경우
- 홀이 파괴되거나 비활성화된 경우

오류가 발생해도 같은 오브젝트에 점수가 반복해서 지급되면 안 된다.

# 9. 미션 시스템

미션은 일반적인 흡수 시스템과 독립적으로 설계한다.

미션 진행도는 레벨 데이터로 정의하며, 모든 미션은 실제 게임플레이 이벤트를 통해 갱신한다.

## 9.1 지원할 미션 타입

최소 다음 종류를 지원한다.

- 특정 오브젝트 수집
- 특정 색상 수집
- 여러 종류의 오브젝트를 각각 정해진 개수만큼 수집
- 시간 부스터 수집
- 특정 오브젝트만 수집
- 특정 Tier의 오브젝트 수집
- 혼합 목표
- 시간 내 목표 개수 달성

예시:

- 빨간 자동차 8대 수집
- 도넛 10개 수집
- 부스터 3개 수집
- 쿠키 6개와 컵케이크 4개 수집
- 사탕 12개, 자동차 6대, 버스 2대 수집

## 9.2 미션 데이터

각 미션에는 다음 정보가 포함되어야 한다.

- 고유 ID
- 미션 타입
- 대상 오브젝트 타입
- 필요한 색상 또는 변형
- 목표 개수
- 현재 진행도
- 완료 여부
- UI 아이콘 참조
- 설명 문자열
- 선택적 보상
- 저장 또는 복원 필요 여부

미션의 진행도는 씬의 GameObject 개수로 계산하지 않는다. 실제로 성공적으로 흡수된 오브젝트 이벤트를 바탕으로 계산한다.

## 9.3 미션 완료 조건

레벨에 미션이 여러 개 있으면 기본적으로 활성 미션을 모두 완료해야 레벨이 클리어된다.

레벨 데이터에서 필요한 경우 특수 조건을 지원할 수 있지만, 임의의 미션을 완료하지 않아도 클리어되는 버그가 있어서는 안 된다.

미션이 완료되면 중복 완료 이벤트가 발생하지 않도록 한다.

미션 완료 연출은 해당 미션이 처음 완료된 시점에 한 번만 실행한다.

## 9.4 미션과 일반 흡수 분리

미션 대상이 아닌 오브젝트도 기본적으로 크기 조건을 충족하면 삼킬 수 있다.

이 경우:

- 성장 경험치는 증가한다.
- 일반 점수가 증가한다.
- 미션 카운트는 증가하지 않는다.
- 미션 대상 여부 때문에 정상 흡수 연출이 생략되지 않는다.

단, `WrongAnswerRule`이 `Penalty` 또는 `Blocked`인 레벨에서는 아래 규칙을 따른다.

## 9.5 오답 처리

오답 처리 방식은 레벨 데이터에서 설정할 수 있어야 한다.

지원 값:

- `None`
- `Penalty`
- `Blocked`

기본값은 `None`이다.

`None`:

- 미션 대상이 아닌 오브젝트도 정상적으로 흡수 가능하다.
- 점수와 성장 경험치를 정상 반영한다.
- 미션 카운트에는 영향을 주지 않는다.
- 추가 벌칙은 없다.

`Penalty`:

- 미션 대상이 아닌 오브젝트를 삼키는 것은 허용한다.
- 흡수 과정은 정상적으로 진행한다.
- 설정된 시간 또는 점수 벌칙을 적용한다.
- 동시에 여러 번 흡수되는 상황에서도 벌칙이 오브젝트당 한 번만 적용된다.
- 남은 시간이 0 이하로 감소하면 정상적인 실패 처리를 수행한다.
- 벌칙 수치를 레벨 데이터에서 조정할 수 있다.

`Blocked`:

- 현재 활성 미션 대상이 아닌 오브젝트는 흡수되지 않는다.
- 오브젝트가 홀에 들어오려 해도 홀 내부로 낙하하거나 소멸하지 않는다.
- 필요하면 막힘 피드백을 표시한다.
- 점수와 성장 경험치를 지급하지 않는다.
- 물체가 홀 내부에 갇히거나 반복 충돌하지 않도록 한다.

`Blocked` 레벨은 반드시 플레이 가능해야 한다. 임무 대상 중 저 Tier 오브젝트가 충분히 존재해야 성장 단계를 거쳐 더 높은 Tier의 임무 대상을 수집할 수 있다.

## 9.6 미션 UI

상단 HUD에 활성 미션을 가로 방향 또는 화면 폭에 맞게 구성한다.

각 미션에는 다음을 표시한다.

- 자체 생성 아이콘
- 대상 오브젝트 식별
- 진행도
- 목표 개수
- 완료 상태

예:

`RED CAR 3/8`

게임 플레이 중 숫자가 갱신되고, 미션 완료 시 시각적 강조를 제공한다.

UI 아이콘에 지원하지 않는 TMP 특수문자를 사용하여 사각형으로 표시되는 문제를 만들지 않는다. 아이콘은 스프라이트 또는 직접 생성한 도형을 사용한다.

# 10. 시간 시스템과 부스터

## 10.1 타이머

레벨별 제한 시간을 지원한다.

일부 초반 레벨은 무제한 시간을 사용할 수 있도록 한다.

타이머가 일시정지 상태에서 감소하지 않도록 한다.

게임 종료 후에도 타이머 이벤트가 실행되지 않도록 한다.

타이머 계산과 UI 갱신을 분리한다.

프레임률이 변하더라도 실제 남은 시간이 의도한 범위에서 유지되어야 한다.

## 10.2 10초 이하 경고

남은 시간이 10초 이하가 되면 경고 연출을 시작한다.

- 타이머 색상 변화
- 부드러운 점멸 또는 펄스
- 선택적 사운드
- 필요에 따른 미세한 강조

화면 전체를 과도하게 번쩍이게 하거나 플레이어의 시야를 방해하지 않는다.

경고 연출은 타이머가 10초 이하로 들어갈 때 한 번 활성화하며, 상태가 바뀔 때 중복 이벤트가 발생하지 않도록 한다.

무제한 레벨에서는 타이머 경고를 실행하지 않는다.

## 10.3 시간 부스터

부스터 오브젝트를 삼키면 지정된 시간을 추가한다.

부스터 데이터에는 다음 항목이 포함된다.

- 추가 시간
- 등장 확률 또는 배치 규칙
- 크기 Tier
- 점수
- 성장 경험치
- 시각적 식별 정보

부스터를 흡수하면 다음이 발생한다.

- 흡수 완료 처리
- 지정된 추가 시간 적용
- 시간 UI 갱신
- 부스터 수집 효과
- 관련 미션 진행도 갱신

무제한 시간 레벨에서는 타이머를 표시하지 않거나 부스터의 시간을 다른 보상으로 처리할 수 있지만, 그 동작을 레벨 데이터에서 명확히 정의한다.

# 11. 점수와 보상

점수는 중앙 계산 시스템에서 관리한다.

점수 계산 항목 예시:

- 오브젝트별 기본 점수
- Tier 보너스
- 연속 흡수 보너스
- 임무 완료 보너스
- 레벨 클리어 보너스
- 남은 시간 보너스
- 오답 벌칙

위 보너스는 전부 필수로 중복 구현할 필요는 없지만, 최종 점수 계산과 UI 갱신은 하나의 일관된 규칙을 사용해야 한다.

점수는 오브젝트당 한 번만 반영한다.

결과 화면에 최종 점수와 보너스를 구분하여 표시할 수 있게 한다.

점수 계산에는 잘못된 음수, 오버플로, Infinity가 발생하지 않도록 방어 코드를 포함한다.

점수 팝업은 화면 가독성을 해치지 않도록 제한하고 풀링을 사용한다.

## 12.1 레벨 진행 검증

각 레벨마다 다음을 검증한다.

- 미션 대상 수량이 실제 생성 수량보다 많지 않은가?
- 필수 오브젝트가 전부 배치되는가?
- 오브젝트 배치가 아레나 범위 안에 있는가?
- 시작 위치에서 이동할 수 있는가?
- 해당 레벨의 미션 대상에 접근할 수 있는가?
- 초기 홀의 Tier로 첫 번째 목표를 삼킬 수 있는가?
- 더 높은 Tier의 목표를 삼키기 전에 충분히 성장할 수 있는가?
- `Blocked` 레벨에서 성장 가능한 미션 대상이 충분한가?
- 제한 시간이 목표에 비해 지나치게 짧지 않은가?
- 완료할 수 없는 미션 조합이 존재하지 않는가?

특히 성장할 수 없는 레벨을 생성해서는 안 된다.

레벨 데이터 검증기에서 미션 대상과 Tier별 성장 경로를 검사한다. 단순히 목표 수량만 비교하지 말고, 실제로 플레이어가 도달할 수 있는 순서를 고려한다.

## 12.2 레벨 다양성

30개 레벨의 모든 오브젝트를 같은 위치와 같은 순서로 배치하지 않는다.

- 테마별 격자 배치
- 특정 구역의 광장
- 작은 오브젝트 밀집 구역
- 큰 오브젝트가 배치된 구역
- 미션 대상이 모여 있는 구역
- 시간 부스터가 배치된 구역
- 이동 동선이 달라지는 배치 패턴

랜덤 요소를 사용하더라도 레벨 검증에 실패한 배치를 만들지 않는다.

같은 Seed와 같은 레벨 데이터를 사용할 때 동일한 배치를 재현할 수 있게 한다.

## 13.1 절차 생성 모델

가능하다면 에디터 도구에서 절차 생성 모델을 만든 뒤 메시, 프리팹, 머티리얼을 실제 에셋으로 저장한다.

예시:

자동차:
- 둥근 차체
- 전면 및 후면
- 지붕
- 창문
- 바퀴
- 타이어와 휠
- 헤드라이트
- 테일라이트

도넛:
- 링 형태의 도형
- 중심 구멍
- 글레이즈
- 토핑
- 디저트에 어울리는 색상 변형

와플:
- 두께가 있는 사각형
- 표면의 격자
- 따뜻한 색감
- 적절한 하이라이트

컵케이크:
- 종이컵 모양
- 부풀어 오른 크림
- 장식
- 색상 변형

오리:
- 몸통
- 머리
- 부리
- 눈
- 날개

도시 오브젝트:
- 차체와 창문이 구분되는 자동차
- 여러 층으로 구성된 버스
- 건물의 층과 창문
- 시각적으로 구분되는 신호등과 소화전

이런 방식으로 형태의 실루엣과 재질이 오브젝트 종류마다 구분되도록 한다.

모델의 폴리곤을 무조건 늘리지 말고, 모바일에서 보기 좋은 로우폴리 스타일을 유지한다.

## 13.2 오브젝트 Tier

각 오브젝트는 다음 데이터를 가진다.

- `ObjectType`
- `ObjectId`
- `Tier`
- `Radius` 또는 논리적 크기
- 기본 점수
- 성장 경험치
- 미션 대상 여부와 별도로 사용할 분류 정보
- 재질 또는 색상 변형
- 풀 ID
- Collider 설정
- 선택적 시간 보너스
- 오답 처리 대상 여부

Tier 숫자가 바뀌면 모든 스크립트에서 같은 규칙을 사용해야 한다.

오브젝트 이름의 문자열을 파싱하여 Tier를 결정하지 않는다. 데이터 필드를 통해 관리한다.

## 13.3 색상별 자동차

자동차는 빨간색, 파란색, 노란색 등 서로 다른 색상 변형을 가진다.

미션에서 빨간 자동차를 목표로 설정했다면 시각적 색상만으로 판정하지 않는다. 실제 `ColorVariant` 또는 명시적 분류 데이터를 이용한다.

머티리얼을 색상별로 공유할 수 있게 구성하여 불필요한 런타임 머티리얼 생성과 GC를 방지한다.

---

# 14. 격자 배치와 군집 배치

기존 `LevelManager.Spawn`이 격자 정렬 및 같은 종류의 이웃 배치를 구현하고 있다면 해당 구조를 분석한 뒤 개선한다.

새로운 스포너를 별도로 만들어 기존 스포너와 중복 작동하게 해서는 안 된다.

## 14.1 배치 기준

- 맵 전체를 격자 셀로 나눈다.
- 시작 위치 주변을 비운다.
- 비어 있는 시작 영역의 크기를 레벨 데이터에서 설정할 수 있게 한다.
- 같은 종류의 물체는 일정한 군집으로 배치한다.
- 물체의 정면이 카메라 방향을 향하게 한다.
- 자동차, 건물 등의 방향이 무작위로 뒤집히지 않게 한다.
- 크기가 큰 물체는 필요한 셀을 충분히 확보한다.
- Collider 간 심한 겹침을 방지한다.
- 이동 동선을 방해하는 배치를 피한다.
- 레벨마다 시각적 구성이 달라지게 한다.

## 14.2 배치 알고리즘

적절한 방법을 선택한다.

가능한 방법:

- 테마별 구역 분할
- 종류별 군집 배치
- 제한된 랜덤 배치
- 주변 셀 탐색
- 우선 배치할 오브젝트와 나중에 배치할 오브젝트 구분
- 배치 이후 겹침 검증

큰 오브젝트부터 배치한 뒤 남은 셀에 작은 오브젝트를 배치하는 방식도 검토한다.

배치 실패가 발생했을 때 무한 루프에 빠지지 않도록 시도 횟수와 재배치 횟수에 상한을 둔다.

배치 결과를 확인한 뒤 필수 미션 수량이 보존되었는지 검증한다.

## 14.3 시작 영역

홀의 시작 위치 주위에는 충분한 여유 공간을 둔다.

첫 번째 미션을 시작하자마자 높은 Tier의 오브젝트에 둘러싸여 이동할 수 없는 문제를 방지한다.

첫 레벨은 이동과 흡수의 핵심 규칙을 학습할 수 있도록 쉬운 오브젝트를 배치한다.

---

# 15. 테마 시스템

최소 다음 테마를 구현한다.

- 디저트
- 도시
- 푸드트럭
- 공원
- 장난감 가게
- 사탕 공장

각 테마는 동일한 아레나 시스템을 공유하지만, 색상과 오브젝트 구성은 달라야 한다.

## 15.1 테마 데이터

각 테마에는 다음 설정을 둔다.

- 배경 색상
- 바닥 색상
- 체크무늬 색상
- 림 색상
- 조명 색상
- 사용 가능한 오브젝트 타입
- 장식 프리팹
- 파티클 색상
- UI 강조 색상
- 배경 음악 또는 분위기 설정

테마별로 완전히 별도의 코드 시스템을 만들지 않는다.

공통 게임 로직은 유지하면서 데이터와 에셋을 변경한다.

## 15.2 시각적 일관성

각 테마는 고유한 분위기를 가지되, 전체 게임의 밝고 장난감 같은 스타일을 유지한다.

테마가 바뀔 때 머티리얼이 갑자기 검게 변하거나, 셰이더가 누락되거나, 오브젝트의 색상 가독성이 떨어지지 않도록 한다.

# 16. 카메라

카메라는 홀을 안정적으로 추적해야 한다.

카메라 시스템에는 다음이 포함된다.

- 부드러운 추적
- 적절한 높이와 기울기
- 홀의 성장에 따른 줌아웃
- 맵 경계에서의 카메라 제한
- 아레나가 커질 때의 시야 조절
- 홀과 주변 오브젝트가 잘 보이는 화면 구성
- UI 영역을 고려한 카메라 프레이밍

홀의 Tier가 증가하면 줌아웃을 적용하되, 순간적으로 카메라가 튀지 않도록 한다.

카메라 이동에 따라 화면의 대상 위치가 급격하게 바뀌는 문제를 방지한다.

카메라 줌은 홀의 실제 크기와 Tier를 참조하여 계산한다. 오브젝트를 먹을 때마다 임의로 확대하거나 축소하지 않는다.

맵이 커질수록 카메라가 필요한 시야를 확보하도록 설정한다.

# 17. 이펙트 시스템

다음 이펙트를 구현한다.

- 흡수 시 끌림 효과
- 흡수 시 회전
- 낙하 효과
- 흡수 완료 파티클
- 홀 내부의 반응
- 성장 시 링 이펙트
- 성장 시 스케일 펀치
- 미션 완료 이펙트
- 점수 팝업
- 시간 부스터 이펙트
- 버튼 반응
- 레벨 클리어 이펙트
- 레벨 실패 피드백

효과를 과도하게 사용하여 플레이어와 오브젝트를 가리지 않도록 한다.

## 17.1 이펙트 풀링

플레이 도중 `Instantiate`와 `Destroy`를 반복하지 않는다.

필요한 이펙트 프리팹을 로딩 시점에 준비하고 풀에서 재사용한다.

기존 `Fx_Swallow` 풀을 확인하고 Prewarm 수를 적절히 확보한다.

동시에 여러 오브젝트가 흡수될 수 있으므로 최대 예상 동시 활성 수를 기준으로 풀 용량을 설정한다.

각 풀에는 다음 기능이 있어야 한다.

- Prewarm
- 최대 크기
- 필요 시 동적 확장 여부
- 활성화 시 초기화
- 반환 시 정리
- 비정상적인 중복 반환 방지

새로운 FX를 추가하면 해당 FX의 풀 용량과 반환 로직도 함께 설정한다.

풀 부족 경고가 반복해서 발생하지 않도록 한다. 그렇다고 모든 FX를 무조건 수백 개씩 생성하여 모바일 메모리를 낭비하지 않는다.

풀의 현재 사용량과 최대 활성 개수를 개발용 디버그 정보로 확인할 수 있게 한다.

# 18. 사운드와 절차 생성 오디오

외부 원작 사운드를 사용하지 않는다.

가능하다면 자체 제작 또는 절차 생성한 짧은 사운드를 사용한다.

필요한 사운드:

- 버튼
- 홀 이동
- 흡수 시작
- 흡수 완료
- 성장
- 미션 완료
- 시간 경고
- 부스터
- 클리어
- 실패
- 레벨 시작

## 18.1 오디오 생성

외부 WAV 파일이 없다면 짧은 파형을 생성하는 방식을 고려한다.

예를 들어:

- 짧은 사인파 또는 주파수 변화로 버튼 사운드 생성
- 여러 파형의 혼합으로 흡수 사운드 생성
- 상승하는 음정으로 성장 피드백 생성
- 짧은 화음으로 미션 완료 표현
- 낮은 음정이나 짧은 하강 효과로 실패 표현

절차 생성 사운드는 과도하게 날카롭거나 반복적으로 피로한 소리가 나지 않도록 한다.

오디오 생성은 에디터에서 실행하고 실제 파일로 저장하거나, 적절한 방식으로 캐시한다. 매 프레임 AudioClip을 생성하지 않는다.

## 18.2 오디오 관리

- Master Volume
- Music Volume
- SFX Volume
- 음소거
- 필요한 경우 진동 설정

오디오가 누락되어도 게임은 정상적으로 실행되어야 한다.

없는 오디오 파일을 참조하거나 Inspector에서 누락된 Clip 때문에 NullReferenceException이 발생하지 않도록 한다.

# 19. UI 설계

- 최고 점수 또는 진행도

버튼을 눌렀을 때 실제로 작동하도록 한다.

## 19.2 인게임 HUD

필수 요소:

- 미션 아이콘

- 성장 게이지

각 요소는 반응형 레이아웃으로 배치한다.

TMP 기본 폰트에 없는 `▶`, `Ⅱ`, `›`, `‹`, `•` 같은 특수문자를 UI 문자열에 사용하지 않는다.

## 19.3 일시정지 화면

- Resume
- Restart
- Home
- Sound

일시정지 시 모든 게임플레이 관련 시간과 흡수 처리가 적절하게 정지되어야 한다.

UI 버튼은 일시정지 상태에서도 반응해야 한다.

## 19.4 클리어 화면

- 최종 점수

- 남은 시간 보너스
- 추가 보상
- 다음 레벨 버튼
- 다시 플레이 버튼
- 홈 버튼

## 19.5 실패 화면

- 실패 메시지
- 최종 점수
- 미완료 미션
- 재도전
- 홈

클리어와 실패 UI가 동시에 표시되면 안 된다.

## 19.6 UI 상호작용

- 버튼이 중복 입력되지 않도록 한다.
- 씬을 재시작해도 이벤트가 중복 구독되지 않는다.
- 비활성화된 패널의 입력이 게임플레이로 전달되지 않는다.
- 버튼을 누르는 동시에 홀도 움직이는 현상을 방지한다.
- 일시정지 화면에서 게임플레이가 실행되지 않도록 한다.

# 20. 저장과 레벨 해금

저장 시스템은 PlayerPrefs를 기본 방식으로 사용할 수 있다.

저장 대상:

- 최고 점수
- 레벨별 최고 점수
- 해금된 레벨
- 완료한 레벨
- 설정
- 조작 모드
- 음량
- 최고 기록 TOP 3

## 20.1 최고 점수 TOP 3

점수 기록은 레벨별로 관리한다.

TOP 3가 어떤 기준인지 명확히 한다. 기본 가정은 각 레벨별 상위 3개 기록이다.

필요한 정보:

- 순위
- 점수
- 레벨
- 기록 데이터의 유효성

기록은 내림차순으로 정렬한다.

새 점수가 기존 TOP 3보다 낮더라도 기존 기록이 손상되면 안 된다.

## 20.2 레벨 해금

처음에는 첫 번째 레벨만 플레이 가능하도록 할 수 있다.

레벨을 클리어하면 다음 레벨이 해금된다.

해금된 레벨은 레벨 선택 화면에서 표시한다.

잠긴 레벨은 실수로 선택해 시작할 수 없도록 한다.

저장 데이터가 누락되거나 잘못된 값이라면 안전한 기본 상태로 복구한다.

## 20.3 저장 데이터 검증

잘못된 PlayerPrefs 값으로 배열 범위 오류나 예외가 발생하지 않도록 한다.

저장 데이터의 버전을 관리할 수 있다.

향후 필드가 추가되더라도 이전 저장 데이터 때문에 게임이 시작되지 않는 문제를 방지한다.

테스트 과정에서 사용자의 기존 저장 데이터를 무조건 초기화하지 않는다. 초기화 기능이 필요하다면 개발용 기능 또는 별도의 사용자 선택 옵션으로 제공한다.

# 21. ScriptableObject와 레벨 데이터

게임의 주요 설정은 Inspector에서 조정할 수 있어야 한다.

필요한 데이터 예시:

- `LevelData`
- `ObjectData`
- `MissionData`
- `ThemeData`
- `HoleGrowthSettings`
- `GameplaySettings`
- `AudioSettings`
- `PoolSettings`

기존 데이터 구조가 적절하다면 그대로 사용한다.

## 21.1 LevelData

각 레벨에 필요한 데이터:

- 레벨 ID
- 레벨 이름
- 테마
- 아레나 크기
- 격자 크기
- 시작 홀 Tier
- 제한 시간
- 무제한 시간 여부
- 오브젝트 생성 목록
- 미션 목록
- 오답 처리 규칙
- 점수 설정
- 성장 설정
- 부스터 설정
- 레벨별 색상
- 카메라 설정
- 다음 레벨 ID
- 검증용 Seed

## 21.2 배열과 참조 검증

레벨 데이터를 읽기 전에 다음을 검사한다.

- 객체가 null인지
- 배열이 비어 있는지
- 레벨 ID가 중복되는지
- 미션 목표값이 유효한지
- 필요한 프리팹이 연결되었는지
- 오브젝트 데이터가 존재하는지
- 필수 아이콘이 존재하는지
- 시작 Tier가 유효한지
- 제한 시간이 음수인지
- 오답 처리 값이 정의되어 있는지

누락된 데이터는 자동 복구 가능한 경우 안전한 기본값을 적용한다.

복구할 수 없는 데이터는 구체적인 오류 메시지를 남기고 해당 레벨의 시작을 안전하게 차단한다.

## 21.3 Resources 폴백 제거

씬의 `LevelData` 배열 참조가 비어 있고 런타임에 Resources 폴백으로 복구되는 기존 경고의 원인을 해결한다.

단순히 경고를 숨기지 않는다.

에셋 생성과 씬 저장 순서를 올바르게 구성한다.

1. LevelData 에셋 생성
2. 실제 레벨 설정 저장
3. 에셋 임포트 완료 확인
4. 씬에 레벨 배열 연결
5. 씬 저장
6. 에셋 연결 검증
7. 최종 씬 재검증

씬이 참조해야 하는 레벨 배열은 Inspector에 직렬화된 실제 참조로 저장되어 있어야 한다.

정상적인 레벨 로딩을 위해 무조건 Resources 폴백에 의존하지 않는다.

# 22. 에디터 자동 생성과 기존 에셋 갱신

기존 `HoleItBuilder` 및 `HoleItFirstOpenSetup` 흐름은 유지한다.

메뉴 경로:

- `HoleIt > 1. 프로젝트 전체 구성`
- `HoleIt > 2. Android APK 빌드`

메뉴가 실제 Unity Editor 메뉴에 등록되어야 한다.

## 22.1 첫 실행 자동 설정

`Assets/Scenes/Main.unity`가 없으면 최초 실행 시 필요한 프로젝트 구성을 생성하고 씬을 열어준다.

`Main.unity`가 이미 존재하면 무조건 덮어쓰지 않는다.

첫 실행 자동 설정 과정에서 다음을 생성하거나 연결한다.

- 필수 폴더
- 기본 머티리얼
- 절차 생성 모델
- 오브젝트 프리팹
- 홀 프리팹
- 이펙트 프리팹
- UI 프리팹
- ScriptableObject
- 레벨 데이터 30개 이상
- 메인 씬
- 필요한 시작 씬
- 참조 연결
- 기본 설정

## 22.2 최초 실행의 반복 방지

`InitializeOnLoad` 또는 `EditorApplication.delayCall`을 사용하는 경우 실행 타이밍을 주의한다.

자동 생성이 반복되어 같은 파일을 계속 덮어쓰거나 Unity 에디터가 멈추는 문제가 없어야 한다.

- 컴파일 도중 실행하지 않는다.
- AssetDatabase 갱신 중 무한 재귀를 만들지 않는다.
- 생성 도중 다시 생성 함수가 호출되지 않도록 한다.
- 작업 완료 상태를 적절히 기록한다.
- 기존 Main 씬이 있으면 보호한다.
- 생성에 실패하면 원인을 기록한다.
- 생성 완료 후 에셋과 씬을 검증한다.

## 22.3 빌더의 멱등성

같은 빌더를 여러 번 실행해도 의미 없는 중복 에셋이 계속 생기지 않아야 한다.

기존 저장 에셋에 값이 바뀌지 않는 문제가 있다면 빌더의 책임과 에셋 소유권을 명확히 정의한다.

생성한 에셋에는 소유 시스템과 스키마 버전을 기록하는 방식을 고려한다.

빌더가 관리하는 생성 에셋은 의도한 설정을 올바르게 갱신한다.

사용자가 직접 만든 별도의 에셋은 무조건 덮어쓰지 않는다.

기존 에셋의 GUID를 불필요하게 변경하지 않는다.

`AssetDatabase` 작업에는 적절한 저장, Import, Refresh 절차를 사용한다. `StartAssetEditing`을 사용한다면 반드시 `try/finally`로 종료를 보장한다.

## 22.4 Editor 코드와 Runtime 코드 분리

`UnityEditor` API는 Editor 전용 폴더 또는 Editor 전용 어셈블리에 둔다.

런타임 코드에서 Editor 전용 타입을 호출하지 않는다.

Android 빌드에서 Editor 전용 코드 참조 때문에 컴파일이 실패하는 문제를 방지한다.

# 23. 메시 생성의 수치 안정성

절차 생성 메시를 만드는 코드는 실제 프로젝트에서 오류가 자주 발생하는 영역이므로 특별히 검증한다.

## 23.1 NaN 및 Infinity 방지

다음 함수를 사용하기 전 입력 범위를 확인한다.

- `Mathf.Pow`
- `Mathf.Sqrt`
- `Mathf.Acos`
- `Mathf.Asin`
- `Mathf.Log`
- `Mathf.Exp`
- 삼각함수와 보간 함수
- 정규화 함수

음수 값에 비정수 지수를 적용하여 NaN이 발생하는 문제를 방지한다.

예를 들어 메시 곡면을 만드는 과정에서 `Mathf.Pow(Mathf.Sin(angle), 0.55f)`를 사용한다면 사인 값의 부호와 입력 범위를 명확히 처리한다.

수학적으로 음수가 나올 수 없는 값은 최소 0으로 제한하고, 각도나 정규화 범위가 필요하면 `Clamp` 또는 `Clamp01`을 적용한다.

## 23.2 메시 검증

메시 생성이 끝나면 다음을 검사한다.

- 정점 개수
- 인덱스 범위
- 삼각형 수
- 정점 좌표 유한성
- 노멀 유한성
- UV 값
- Submesh 범위
- Bounds의 유한성
- Bounds 크기의 유효성
- Collider에 사용할 수 있는 형상인지

정점 좌표, Bounds 또는 노멀에 NaN이나 Infinity가 있으면 조용히 진행하지 말고 해당 메시 이름과 생성 단계가 포함된 오류 메시지를 출력한다.

Unity에서 `Invalid worldAABB`가 반복해서 발생하지 않도록 한다.

메시의 정점 수가 너무 커서 모바일에서 메모리를 과도하게 사용하지 않도록 한다.

메시 Index Format과 인덱스 범위를 점검한다. 16비트 인덱스로 충분하지 않은 경우 적절한 형식을 사용하되 모바일에서의 비용을 고려한다.

## 23.3 노멀과 메시 방향

메시가 뒤집혀 보이거나 안쪽 면이 사라지는 문제를 방지한다.

- 삼각형 인덱스 순서
- 노멀 방향
- Cull 설정
- 접합부
- 메시 중심
- 바닥 접지
- Collider 방향

각 모델을 실제 씬에서 렌더링하여 육안으로 확인하는 것이 가능하면 그렇게 한다.

# 24. C# 회귀 방지

이 프로젝트에서 이미 발생한 컴파일 오류를 반드시 방지한다.

## 24.1 미정의 함수

`Prim(...)`처럼 정의되지 않은 헬퍼를 호출하여 Editor 어셈블리 전체가 실패하는 문제를 반복하지 않는다.

새로 호출하는 모든 함수, 타입, 변수, 상수는 실제 정의가 있어야 한다.

리팩터링 과정에서 함수 이름만 변경하고 호출부가 남아 있는 문제를 방지한다.

생성 코드 전체에서 정의와 사용 관계를 확인한다.

## 24.2 CS0136 및 중복 변수

C#의 지역 변수 선언 공간과 switch/case 규칙을 지킨다.

특히 다음 문제를 방지한다.

- `CS0136`
- `CS0128`
- 중복 지역 변수
- 같은 이름의 잘못된 패턴 변수
- 같은 타입의 중복 정의
- 네임스페이스 충돌

switch/case 내부에서 각 case의 변수명이 충돌할 수 있다면 고유한 변수명을 사용하거나 적절히 독립된 중괄호 블록을 사용한다.

코드를 자동 생성하는 경우 생성된 파일 전체를 다시 검사한다.

## 24.3 Unity 6 API

실제 Unity 버전을 확인하고 해당 버전에서 올바르게 사용할 수 있는 API를 사용한다.

필요에 따라 다음을 사용한다.

- `Rigidbody.linearVelocity`
- `FindFirstObjectByType`
- `TMP_Text.textWrappingMode`

구버전 API로 무조건 되돌려 호환성 문제를 숨기지 않는다.

사용할 API가 실제 프로젝트의 Unity 버전에 존재하는지 확인한다.

## 24.4 직렬화 필드

에디터 빌더가 `SerializedProperty`나 기타 직렬화 API로 값을 연결한다면 필드명을 실제 코드의 필드와 일치시킨다.

예를 들어 `SetRef`를 호출할 때 대상 필드가 실제로 존재하는지 확인한다.

직렬화 필드를 변경하면 에디터 자동 생성 코드, 테스트 코드, 기존 프리팹과 씬 참조를 함께 확인한다.

# 25. 성능 요구사항

목표는 지원 가능한 모바일 기기에서 안정적인 60fps에 최대한 근접하는 것이다.

기기 사양에 따라 60fps를 보장할 수는 없으므로 실측 가능한 조건과 제한을 별도로 보고한다.

## 25.1 플레이 중 Instantiate 금지

게임플레이 상태인 `Playing`에 들어간 뒤에는 불필요한 `Instantiate`와 `Destroy`를 사용하지 않는다.

로딩 또는 초기화 시점에 필요한 프리팹과 이펙트를 준비한다.

플레이 중 새로 필요한 객체는 기존 풀에서 가져온다.

예외가 필요하면 게임의 핵심 반복 루프를 방해하지 않는 구조인지 검토한다.

## 25.2 메쉬 결합과 드로우 콜

재질별 메시 결합은 정적인 배경 장식이나 정적 환경 메시를 대상으로 적용한다.

흡수 대상 물체는 개별로 이동하고 사라져야 하므로 동적 오브젝트 전체를 하나의 메시로 결합하지 않는다.

동적 오브젝트는 다음 방법을 검토한다.

- 공유 메시
- 공유 머티리얼
- 가능한 경우 GPU Instancing
- 오브젝트 내부의 재질별 메시 결합
- 불필요한 자식 Renderer 감소
- 적절한 Collider 구성

정적 장식은 재질별 결합을 고려한다.

메시 결합으로 오브젝트의 독립적인 흡수 기능이 깨지지 않도록 한다.

## 25.3 렌더링 비용

- 불필요한 실시간 그림자 감소
- 그림자 거리 제한
- 적절한 라이트 구성
- 과도한 투명 오브젝트 제한
- 파티클의 최대 개수 제한
- 머티리얼 공유
- 불필요한 재질 인스턴스 방지
- 화면 밖에서 필요한 최소한의 처리
- 필요에 따라 거리 기반 장식 디테일 조정
- 적절한 카메라 클리핑 평면

모바일에서 셰이더 비용이 지나치게 높아지지 않도록 한다.

## 25.4 GC와 메모리

- 매 프레임 새로운 배열과 리스트 생성 방지
- 불필요한 LINQ 호출 최소화
- 반복적인 문자열 생성 최소화
- 반복적인 씬 전체 오브젝트 검색 방지
- 코루틴의 불필요한 생성 제한
- 풀에서 반환한 객체의 참조 정리
- 이벤트 구독과 해제 관리
- 네이티브 리소스 해제
- 씬 전환 후 비활성화된 참조 정리

실제 Profiler나 실행 도구를 사용할 수 없다면 측정한 것처럼 보고하지 않는다.

# 26. 저장 및 로딩 시나리오

게임의 모든 상태를 저장할 필요는 없지만, 사용자가 기대하는 진행 상황은 유지되어야 한다.

다음 상황을 검증한다.

- 첫 실행
- 저장 데이터가 없는 상태
- 레벨 클리어 후 앱 종료
- 다시 실행 후 해금 상태 복원
- 설정 변경 후 재실행
- 최고 점수 변경 후 재실행
- 잘못된 저장값
- 상위 버전에서 하위 버전 또는 이전 버전의 데이터가 존재하는 경우

게임 실행에 필요한 기본 데이터와 사용자 진행 데이터를 분리한다.

레벨 에셋을 직접 PlayerPrefs에 저장하려 하지 않는다. 저장할 값은 안정적인 레벨 ID 및 기록 데이터로 관리한다.

# 27. 오류 처리 및 복구

오류를 단순히 `try/catch`로 숨기지 않는다.

예외가 발생하면 원인과 관련 객체를 찾을 수 있도록 기록한다.

다음은 반드시 검증한다.

- 레벨 데이터 누락
- 프리팹 누락
- 머티리얼 누락
- 셰이더 누락
- UI 참조 누락
- 미션 대상 누락
- 배열 범위 초과
- 생성 불가능한 오브젝트 배치
- 중복 이벤트
- 중복 점수
- 풀 반환 오류
- 씬 로딩 실패
- 저장 데이터 파싱 실패
- 비정상적인 숫자 값
- 에디터 자동 설정 중 중단
- Android 빌드 설정 오류

복구할 수 있는 데이터라면 안전한 기본값을 사용한다.

복구할 수 없는 경우에는 명확한 에러 메시지를 기록하고, 게임이 무한 루프나 NullReferenceException 연쇄로 넘어가지 않도록 처리한다.

- 일시정지와 재개

## 28.7 에셋 및 메시 검사

- 모든 메시의 Bounds가 유한한가?
- NaN 또는 Infinity가 존재하지 않는가?
- 누락된 머티리얼이 없는가?
- 누락된 프리팹이 없는가?
- 참조가 비어 있는 레벨 데이터가 없는가?
- 모든 주요 프리팹에 필요한 Collider가 있는가?
- 잘못된 메시 인덱스가 없는가?
- 모바일에 불필요하게 고해상도인 텍스처가 없는가?

## 28.8 레벨 전체 검사

30개 이상의 레벨마다 자동 검증을 수행한다.

각 레벨에서 다음을 확인한다.

- 고유 ID
- 필수 데이터
- 유효한 테마
- 미션 개수
- 목표 수량
- 실제 생성 수량
- Tier별 성장 경로
- 오답 규칙
- 타이머
- 격자 배치
- 시작 공간
- 오브젝트 배치 성공 여부

테스트할 수 있다면 최소한 모든 레벨이 로드되고 초기 오브젝트 배치가 끝나는지 확인한다.

실제 완주 테스트를 수행하지 않았다면 모든 레벨을 완주했다고 주장하지 않는다.

## 28.9 장시간 및 회귀 검사

반복해서 실행 가능한 경우 다음 테스트를 수행한다.

- 연속 재시작

- 연속 흡수

이벤트 누적, 메모리 누수, 풀 부족, 입력 불능, 타이머 중복, 클리어 중복 등의 문제를 찾는다.

# 31. 최종 파일 생성과 제출 절차

모든 구현이 끝나면 아래 순서대로 처리한다.

1. 프로젝트 안의 컴파일 관련 오류를 검사한다.
2. 생성 파일 간 중복 클래스와 중복 함수가 없는지 검사한다.
3. `CS0136`, `CS0128`과 같은 지역 변수 충돌 가능성을 확인한다.
4. 미정의 함수·타입·필드가 없는지 확인한다.
5. 모든 ScriptableObject가 올바르게 저장되었는지 확인한다.
6. 모든 핵심 씬 참조가 직렬화되었는지 확인한다.
7. 프리팹 및 머티리얼의 누락 참조를 확인한다.
8. 레벨 데이터가 30개 이상 존재하는지 확인한다.
9. 메인 씬이 ZIP 내부에 존재하는지 확인한다.
10. `Packages`와 `ProjectSettings`를 포함한다.
11. README와 빌드 보고서를 포함한다.
12. 불필요한 캐시를 제외하고 ZIP을 생성한다.
13. ZIP 무결성을 검사한다.
14. ZIP을 다시 열어 필수 파일을 확인한다.
15. 최종 ZIP 파일의 실제 크기를 확인한다.
16. 다운로드 가능한 정확한 경로를 확인한다.
17. 최종 보고서를 작성한다.

가능하다면 Unity를 사용한 실제 컴파일과 빌드를 수행한다. 실행 환경상 불가능한 작업은 수행하지 못한 이유를 분리하여 보고한다.

# 32. 최종 완료 기준

아래 조건을 가능한 범위에서 충족해야 한다.

- 기존 프로젝트가 보존되어 있다.
- Unity 6000.3.6f1 프로젝트로 열 수 있는 구조다.
- Built-in Render Pipeline을 유지한다.
- 세로 화면 모바일 플레이를 지원한다.
- 드래그 입력과 고정 조이스틱 선택 기능이 있다.
- 홀의 3D 외형과 스텐실 처리가 구현되어 있다.
- 홀 성장과 Tier 판정이 일관적이다.
- 흡수 애니메이션이 실제로 작동한다.
- 점수와 성장 경험치가 중복 지급되지 않는다.
- 임무 시스템이 동작한다.
- `None`, `Penalty`, `Blocked`가 구분된다.
- 시간과 부스터가 연결된다.
- 클리어·실패·재시작·일시정지가 작동한다.
- 최소 30개 레벨 데이터가 실제 존재한다.
- 레벨마다 미션과 배치가 다르다.
- 테마별 표현이 구현되어 있다.
- PlayerPrefs 기반 저장이 동작한다.
- 레벨 해금과 TOP 3 기록이 연결되어 있다.
- 에디터 자동 생성 도구가 존재한다.
- 빌더 재실행 시 불필요한 중복 에셋이 만들어지지 않는다.
- `Main.unity`가 없을 때 자동 설정 흐름이 유지된다.
- 모든 핵심 에셋 참조가 실제로 저장되어 있다.
- 메시 생성에서 NaN 및 Infinity가 차단된다.
- 입력 시스템 설정이 런타임 코드와 일치한다.
- 플레이 중 불필요한 Instantiate/Destroy가 반복되지 않는다.
- 실제 수행한 컴파일 및 테스트 결과가 기록되어 있다.
- 해결하지 못한 문제는 숨기지 않는다.
- 완성된 Unity 프로젝트 ZIP이 실제 생성되고 검증되었다.

모든 조건을 충족하지 못한 부분은 실패 또는 미검증 상태를 명확히 기록한다.

실제 실행 또는 빌드를 하지 못한 항목, 원인, 사용자가 Unity에서 확인해야 할 사항을 작성한다.
